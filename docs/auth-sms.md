# ثبت‌نام و بازیابی رمز با موبایل

## رفتار جدید

- ثبت‌نام ایمیلی: نام کامل، ایمیل، **موبایل اجباری** و رمز قوی؛ سپس تأیید مالکیت موبایل با کد پیامکی. پیش از تأیید، حساب یا نشست ساخته نمی‌شود.
- شماره در هویت Better Auth (`user.phoneNumber`) و با `phoneNumberVerified: true` ثبت می‌شود، نه فقط در پروفایل سفارش‌ها.
- ارقام فارسی/عربی و پیش‌شماره‌های `+98` و `0098` به شکل یکسان `09xxxxxxxxx` تبدیل می‌شوند؛ این قانون روی فرم، Server Action و API مستقیم اعمال می‌شود.
- «فراموشی رمز»: کد یک‌بارمصرف و تعیین رمز جدید. رمز فعلی قابل بازیابی نیست و **هیچ‌وقت پیامک نمی‌شود**.
- کد ۵ رقمی، اعتبار ۵ دقیقه، حداکثر ۵ تلاش برای هر کد. سقف تکمیلی تلاش و فاصلهٔ ۹۰ ثانیه‌ای ارسال مجدد در سرور نیز اعمال می‌شوند.
- ارسال دوباره، کد قبلی همان کاربرد را باطل می‌کند. کد ورود، کد بازنشانی رمز و شماره‌های مختلف قابل جایگزینی با یکدیگر نیستند.
- پس از تغییر رمز، نشست‌های قبلی در سرور لغو می‌شوند. کش کوکیِ موجود پروژه ممکن است تا ۳۰ ثانیه وضعیت قبلی را نشان دهد؛ این تنظیم قبلی تغییر نکرده است.
- برای شمارهٔ ناشناخته یا تأییدنشده پاسخ عمومی داده می‌شود؛ وجود حساب از مسیر فراموشی رمز افشا نمی‌شود.
- خطای سرویس پیامک، حتی خطای منطقی داخل پاسخ HTTP 200، به‌عنوان ارسال موفق نمایش داده نمی‌شود. متن خام پاسخ سرویس (که ممکن است اطلاعات حساس داشته باشد) در لاگ چاپ نمی‌شود.

## حساب‌های قدیمی

در «پروفایل ← اطلاعات حساب ← امنیت و بازیابی حساب» شمارهٔ بازیابی را با پیامک تأیید کنید. شمارهٔ تماس سفارش‌ها جداست و ویرایش آن، شمارهٔ بازیابی را تغییر نمی‌دهد.

شماره‌های قدیمیِ موجود در `profiles.phone` خودکار به هویت منتقل نمی‌شوند: وجود یک شماره در فیلد تماس، اثبات مالکیت آن نیست. بدون دسترسی به شمارهٔ تأییدشده، کاربر باید از مسیر پشتیبانی و احراز مالکیت حساب اقدام کند.

برای جلوگیری از اتصال هم‌زمان یک شماره به دو حساب، ایندکس یکتای جزئی `malli_user_phone_unique` هنگام نخستین ثبت/تأیید شماره ساخته می‌شود. حساب‌های قدیمیِ بدون شماره مجاز باقی می‌مانند. حساب MongoDB باید مجوز `createIndex` داشته باشد. اگر از قبل شماره‌های تکراری/غیرنرمال در مجموعهٔ هویت وجود دارد، پس از پشتیبان‌گیری آن‌ها را با بررسی مالکیت اصلاح کنید؛ کد هیچ حسابی را حذف یا خودکار ادغام نمی‌کند.

## تنظیمات لازم روی هاست

**پیش از انتشار نسخهٔ جدید، ارسال پیامک را روی هاست بررسی کنید؛ ثبت‌نام جدید بدون تأیید پیامکی کامل نمی‌شود.**

متغیرهای سرور را در محیط اجرای برنامه یا فایل محیطیِ خارج از Git تنظیم کنید؛ کلیدها نباید `NEXT_PUBLIC_` باشند یا داخل مخزن/پیام پشتیبانی قرار بگیرند.

| متغیر                | کاربرد                                                       |
| -------------------- | ------------------------------------------------------------ |
| `MONGODB_URI`        | اتصال دیتابیس واقعی، با تنظیم صحیح `authSource` در صورت نیاز |
| `BETTER_AUTH_URL`    | نشانی HTTPS واقعی سایت                                       |
| `BETTER_AUTH_SECRET` | راز تصادفی و پایدارِ احراز هویت؛ در Build و اجرا تنظیم باشد  |
| `SMS_API_KEY`        | کلید پنل IPPanel فعلی پروژه                                  |
| `SMS_FROM_NUMBER`    | خط فرستندهٔ مجاز همان پنل                                    |
| `SMS_PATTERN_CODE`   | شناسهٔ الگوی تأییدشده؛ الگو باید پارامتر `code` را بپذیرد    |

برای استفاده از واسط پیامک، به‌جای اتصال مستقیم:

- `SMS_RELAY_URL`: آدرس HTTPS واسط مورد اعتماد؛ اطلاعات کلید پنل روی واسط نگهداری شود.
- `SMS_RELAY_SECRET`: راز مشترک؛ در هدر `x-relay-secret` ارسال می‌شود.
- بدنهٔ درخواست واسط: `{ "phone": "شماره", "code": "کد یک‌بارمصرف" }`.
- واسط باید شکست ارسال را با وضعیت HTTP ناموفق یا `ok: false`/`success: false` اعلام کند.

در اجرای چندپردازه یا چندسروری، `UPSTASH_REDIS_REST_URL` و `UPSTASH_REDIS_REST_TOKEN` را تنظیم کنید تا محدودیت‌ها بین نمونه‌ها مشترک باشند. بدون Redis، محدودیت تکمیلی در حافظهٔ همان پردازه است.

کلیدهای GitHub، پیامک و دیتابیس را در Git ذخیره نکنید. حذف یک فایل از آخرین نسخه، اطلاعات قبلی آن را از تاریخچهٔ Git پاک نمی‌کند؛ راز افشاشده باید تعویض شود.

## اصلاحات فرم‌ها

- لرزش فقط یک‌بار روی قاب بیرونی فیلد اجرا می‌شود؛ دیگر قاب داخلی هم‌زمان جابه‌جا نمی‌شود.
- اطراف محتوای اسکرول‌شوندهٔ فرم ورود فاصلهٔ کافی برای حاشیه و حلقهٔ فوکوس وجود دارد؛ پوشش‌های برش‌دهندهٔ مراحل کد و بازنشانی حذف شده‌اند.
- اولین خطا داخل **همان فرم** فوکوس می‌گیرد و پیش از لرزش در دید قرار می‌گیرد؛ فیلد هم‌نام در پشت دیالوگ انتخاب نمی‌شود.
- خطاها خوانا و متصل به فیلد با `aria-describedby` و `aria-invalid` هستند؛ اعلان اضافیِ پوشانندهٔ فرم حذف شده است.
- کد پیامکی یک ورودی واقعی با نمایش پنج خانه است: جای‌گذاری، تکمیل خودکار پیامک، ارقام فارسی، انتخاب متن و پاک‌کردن طبیعی کار می‌کنند.
- ارسال تکراری با کلیک/Enter سریع مسدود می‌شود؛ ارسال مجدد دارای وضعیت انتظار و محدودیت سروری است.
- فونت ورودی روی موبایل ۱۶ پیکسل است؛ فوکوس باعث زوم خودکار رایج iOS نمی‌شود. حالت کاهش حرکت، لرزش را غیرفعال می‌کند.
- متن قدیمیِ تبلیغ قابلیت پرو مجازی در پنل ورود با توضیح قابلیت‌های موجود جایگزین شد.

## تست و انتشار

Node.js نسخهٔ ۲۲ و وابستگی‌های توسعه لازم‌اند:

```bash
npm ci
npm run test:auth
npx playwright install --with-deps chromium
npm run test:ui
npm run lint
npx tsc --noEmit
npm run build
```

`test:auth` شامل ۱۱ تست سرور است. `test:ui` همان تست‌ها و ۱۴ تست مرورگر را اجرا می‌کند (جمعاً ۲۵ تست). موارد بررسی‌شده: موبایل اجباری و نرمال‌سازی، ثبت هویت، بازنشانی رمز، لغو نشست، کد نادرست/منقضی/تکراری، محدودیت تلاش/ارسال، مسابقهٔ هم‌زمان ثبت‌نام، شمارهٔ حساب قدیمی، شکست سرویس، تأیید رمز، ارسال تکراری و برش فیلدها در عرض‌های ۳۲۰، ۳۷۵، ۳۹۰، ۷۶۸ و ۱۲۸۰ پیکسل با تم روشن/تیره.

تست‌ها دیتابیس MongoDB موقت و سرویس پیامک محلی می‌سازند؛ به دیتابیس و پنل پیامک واقعی وصل نمی‌شوند. مؤلفه‌های فرم، CSS، اکشن‌های سرور و تنظیمات Better Auth واقعی‌اند؛ برای اجرای سبک، لایهٔ انتقال Next Server Actions و Image/navigation در محیط تست سازگار شده‌اند. این مجموعه جای آزمون کامل سایت، مرورگرهای دیگر یا تحویل واقعی پیامک روی هاست را نمی‌گیرد.

Build تولیدی با متغیرهای آزمایشی احراز هویت و بدون دیتابیس واقعی بررسی شد. خروجی آزمایشی Build را منتشر نکنید؛ روی محیط انتشار، Build را با مقادیر واقعی محیط انجام دهید. پس از Pull روی هاست، وابستگی‌ها و Build را به‌روزرسانی و برنامهٔ Node.js را Restart کنید. کل پوشهٔ سورس را به‌عنوان فایل استاتیک در `public_html` کپی نکنید.
